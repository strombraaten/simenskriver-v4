# Astro's content cache serves stale HTML after remark/rehype plugin changes

## Context

Astro's content layer stores rendered post HTML in `node_modules/.astro/data-store.json`. Cache entries are keyed off the **content files**, not off the code that renders them. A remark or rehype plugin change therefore does **not** invalidate the cache: unchanged `.md` files keep returning their previously rendered HTML.

Locally this is masked, because `pnpm dev` sets `ASTRO_CONTENT_COLLECTION_CACHE=false` — dev always re-renders. `pnpm build` did not, so builds could reuse the cache.

Vercel restores `node_modules` between deployments, so the stale data store survives across deploys. The result is a deploy that "succeeds" while shipping pre-change HTML — indistinguishable from a fix that simply does not work.

## How it showed up

A fix to `remark-obsidian-embeds.ts` (stop force-embedding titled YouTube links) rendered correctly in `pnpm dev` and in a clean local build, was merged, and Vercel reported a successful production deploy — but the live page still served the old markup.

## How to confirm it is this, and not a broken fix

Reproduce the cache hit locally; do not rely on `pnpm dev`:

```sh
# 1. Build with the OLD code and a clean cache -> poisons the data store
rm -rf .astro node_modules/.astro && pnpm exec astro build

# 2. Restore the NEW code and rebuild WITHOUT clearing the cache
pnpm exec astro build
# If the output is still the old markup, the cache is the cause, not the code.
```

Inspect the built file directly rather than the browser — `dist/<slug>/index.html` is the ground truth for what deploys.

## Solution

`pnpm build` runs `astro build --force`, which clears the content layer cache before building. Correctness beats incremental speed here: a full re-render of ~180 posts costs a few seconds, while a silently stale deploy costs a debugging session.

Do not remove `--force` to speed up builds without another invalidation mechanism in place.

## Related gotcha

Production response headers come from the committed `vercel.json` (generated by `scripts/generate-deployment-config.js`), **not** from the `csp:` block in `astro.config.mjs`. Vercel reads `vercel.json` when the deployment is created, before the build runs — so a `vercel.json` regenerated during the build does not affect that same deploy. When adding an embed provider, update the CSP in `scripts/generate-deployment-config.js` and commit the regenerated `vercel.json`.
